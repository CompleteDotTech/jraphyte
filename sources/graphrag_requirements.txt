Extend the **existing TRACE-GC project** to make GraphRAG and graph-aware retrieval first-class architectural components.

## Critical starting assumption

TRACE-GC has **already been updated** with the previously specified improvements.

Do **not** reimplement, duplicate, rename unnecessarily, or replace those improvements.

Assume the current TRACE-GC architecture already contains, at minimum:

- Evidence Firewall
- claim-to-source verification
- explicit semantic outcome vs confidence separation
- Minimum Evidence Closure
- Question Packing Planner
- probability vs policy-score separation
- hierarchical / beam-search reasoning where applicable
- deterministic constraint compilation
- an explicit Synthesizer / Resolver above Jev
- abstention and evidence-acquisition states
- expanded Decision IR
- exact Jev model-version pinning and provenance
- empirical calibration
- uncertainty bands rather than universal `0.5` thresholds
- question-set autoresearch
- question redundancy analysis
- error-driven synthesis research
- decision/provenance ledger
- counterfactual replay
- transactional and reversible graph mutations
- graph-operation risk classes
- evaluation / ablation infrastructure
- the improved evidence-gated TRACE-GC architecture produced by the previous upgrade

First inspect the current project and determine how these are already implemented.

**Integrate GraphRAG into that architecture rather than creating a parallel architecture.**

Do not regress any existing behavior.

---

# Primary objective

Add a complete **bidirectional GraphRAG subsystem** to TRACE-GC.

Graph retrieval should operate in two different roles:

```text
1. UPSTREAM GRAPH-AWARE RETRIEVAL

Existing graph
    ↓
retrieve useful graph context
    ↓
TRACE-GC synthesis / validation
    ↓
new graph mutation


2. DOWNSTREAM GRAPHRAG

Compiled evidence graph
    ↓
GraphRAG retrieval
    ↓
search / QA / agents / research / discovery
```

These two roles must remain architecturally distinct but share infrastructure where appropriate.

The result should produce a continuous loop:

```text
retrieve
   ↓
understand
   ↓
synthesize
   ↓
validate
   ↓
compile
   ↓
commit
   ↓
retrieve again
```

# 1. Preserve the core responsibility boundaries

Make these distinctions explicit throughout the architecture and implementation:

```text
GraphRAG
    = determines WHERE relevant graph knowledge may exist

Evidence Retrieval
    = finds candidate source material and graph context

Evidence Firewall
    = determines whether retrieved material is usable evidence

Jev
    = makes bounded semantic judgments about evidence

Synthesizer / Resolver
    = reconciles competing semantic judgments and graph hypotheses

Constraint Compiler
    = determines whether proposed graph structure satisfies deterministic rules

Mutation Planner
    = determines the exact proposed persistent changes

Transaction Engine
    = commits, rolls back, supersedes, or repairs graph state

TRACE-GC
    = controls whether evidence ultimately becomes graph state
```

GraphRAG must **never become the arbiter of graph truth**.

A retrieved graph fact may be:

- correct
- incomplete
- outdated
- contradicted
- derived from weak evidence
- superseded
- context-specific
- relevant only for candidate generation

Retrieval therefore produces **candidate context**, not automatically trusted truth.

# 3. Create explicit upstream GraphRAG

Add graph-aware retrieval **before semantic synthesis**.

When TRACE-GC evaluates a new candidate assertion, it should be able to query the existing graph for context such as:

```text
candidate entity neighborhood
known aliases
possible duplicate entities
current entity type
historical entity types
existing relationships
neighboring relationships
multi-hop paths
ownership hierarchy
organizational hierarchy
ontology ancestors
ontology descendants
schema restrictions
existing evidence
contradicting evidence
prior decisions
superseded decisions
related claims
temporal relationships
graph communities
source provenance
previous merge/split history
```

Example:

```text
New source:

"Acme acquired Foo in March 2024."

Candidate:

Acme --acquired--> Foo
```

Before asking Jev to judge the candidate, GraphRAG may retrieve:

```text
Acme
 ├── owns → Bar
 ├── partneredWith → Foo
 └── alias → Acme Holdings

Foo
 ├── subsidiaryOf → Baz
 ├── previousOwner → Qux
 └── relevant evidence E12, E29

Existing graph path:
Acme → partneredWith → Foo

Historical decision:
D221 rejected previous sameAs(Acme,Foo)

Ontology:
acquired:
    domain Organization
    range Organization

Temporal evidence:
Foo subsidiaryOf Baz until Feb 2024
```

That context can become part of the **Minimum Evidence Closure** if relevant.

GraphRAG should therefore feed the existing:

```text
Minimum Evidence Closure
```

component rather than bypass it.

Define:



The goal is **not to bolt GraphRAG onto the end**.

The goal is to make the graph itself an actively queried evidence substrate for subsequent graph synthesis while also exposing the compiled graph as a high-quality, provenance-aware GraphRAG substrate for downstream users and agents.

The finished TRACE-GC system should therefore support the complete cycle:

> **retrieve from evidence and graph state → evaluate evidence → synthesize candidate knowledge → compile and validate → transactionally update the graph → expose the improved graph through GraphRAG → use that graph to improve future synthesis.**
